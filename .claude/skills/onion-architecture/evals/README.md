# onion-architecture evals

Regression fixtures for the `onion-architecture` skill, shipped inside the skill
folder so they travel with it (e.g. via `package_skill.py` or any future
skill-delivery command).

## Layout

- `evals.json` — the test-case manifest: one entry per fixture, with the
  review prompt sent to whatever's under test.
- `expected-findings.json` — the answer key: per case, `expected_findings`
  (file/section/anti-pattern/description a passing review must surface) and
  `known_false_positives` (things a reviewer must *not* flag, because they're
  the codebase's actual convention, not a violation). Kept separate from
  `fixtures/` on purpose — it must never be visible to whatever is under test.
- `fixtures/case-N-<name>/` — small, self-contained mini codebases (7-ish
  files each: `routes.ts`/`service.ts`/`repository.ts`/`contracts.ts` plus
  local mocks of `container.ts`/`db.ts`/`shared.ts`) styled after
  `server/src/modules/<name>/` or `reviewer-core/src/**`. Each fixture has
  exactly 3 planted violations.

## The blind-fixture rule

Fixture files must contain **zero** comments, TODOs, or naming that hints at
the planted violation (no `// BUG`, no `// violates onion architecture`, no
suspiciously named `badService.ts`). A reviewer — human, generic LLM, or
skill-assisted agent — must find the issue by reading the code the same way
it would read a real PR. If a fixture stops reading like plausible production
code, fix the fixture, not the assertion.

## Running an eval

Point a reviewer at `fixtures/case-N-<name>/` with the `prompt` from
`evals.json`, and check its findings against that case's `expected_findings`
in `expected-findings.json`. To compare skill-assisted vs. baseline
(unassisted) review quality, run the same prompt twice — once through an
agent with access to this skill (e.g. the `architecture-reviewer` subagent),
once through a generic agent explicitly told not to consult any skill — and
grade both against the same answer key.

Known false-positive to watch for in both conditions: don't let a reviewer
flag `new XRepository(container.db)` (a module constructing its *own*
repository) as a container-bypass violation — that's the established
same-module pattern (see `server/src/modules/repos/service.ts`).
`container.<x>Repo` getters exist for *cross*-module access only. `case-1` and
`case-2`'s `known_false_positives` entries exist specifically to catch a
grader that doesn't check for this.

## Where run output goes

This folder holds only the fixtures and the manifest — nothing generated by
actually *running* an eval (per-run transcripts, grading.json, benchmark
summaries, CI logs). Those belong in the sibling
`.claude/onion-architecture-eval-runs/` directory, which is gitignored except
for its own README.

## Adding a new case

1. Pick 2-4 anti-patterns from `../references/anti-patterns.md` (or a new one
   worth covering) and write a plausible module/file around them.
2. Add the case to `evals.json` with a prompt.
3. Add the planted issues (and any expected false-positive traps) to the
   matching case in `expected-findings.json`.
4. Read the fixture back as if you'd never seen it — if anything gives away
   the answer, rewrite it.
